# Visit Log: Patient Visit Tracker

A small internal tool for recording and reviewing patient visits by clinicians. Node.js, Express and SQLite (Node's built-in `node:sqlite`) on the back end; React, TypeScript, TanStack Query, Tailwind CSS and shadcn/ui on the front end.

> Demo data only. Do not enter real patient information.

## Quick start

Requires Node.js 22.13 or later (current LTS). There are no native modules to compile, so `npm install` works on any OS. Node prints an `ExperimentalWarning` for `node:sqlite` on start — that's expected.

```bash
npm install
npm run seed   # demo clinicians, patients and visits (resets existing rows)
npm run dev    # API on http://localhost:3001, app on http://localhost:5173
```

Other commands:

```bash
npm test              # API and UI tests
npm run typecheck      # TypeScript, both packages
npm run lint -w client
```

The database is a local SQLite file (`server/visits.db`), created on first start. Set `DB_FILE` to use a different path.

## What it does

- **Summary strip:** visits today, visits in the last 7 days, and patients not seen in 7+ days (click to filter the roster to just them).
- **Roster** of patients and clinicians with search, avatar initials, and "last seen". Overdue patients get a "Needs visit" badge, with a toggle to show only them.
- **Visits** newest first, as a day-grouped timeline or a table — switchable. Select a patient and/or clinician (or click a name in the timeline) to filter; filters combine and show as removable chips.
- **Record visit** in a side sheet: searchable patient and clinician pickers, one-tap times ("Just now", "30 min ago", "1 hour ago") or a custom date/time, and notes. Prefilled from whatever filter is active.
- **Add patients and clinicians** from the roster.
- Loading skeletons, empty states with context-aware messages, toast confirmation on save, and inline server errors.

## How the UI was designed

I assumed the main user is a care coordinator or clinician who opens this tool to answer two questions: what happened recently, and who hasn't been seen. That's why the first things on screen are the summary and "last seen" labels, why the roster sits beside a timeline instead of two plain tables, and why recording a visit is a few taps rather than a full-page form. The components come from shadcn/ui, built on Radix primitives (so keyboard and screen-reader support come for free), re-themed with a calm clinical palette — pine for actions, amber reserved only for "needs a visit" — and the Atkinson Hyperlegible typeface, designed for low-vision readers. More detail, including a decision I reversed, is in [docs/decisions.md](docs/decisions.md).

## Structure

```
server/src
  db/            schema.sql, connection (node:sqlite), seed
  repositories/  all SQL lives here
  routes/        thin HTTP handlers
  validation.ts  zod schemas (input validation + inferred types)
  errors.ts      central error handling
  app.ts         builds the Express app (no listen, so tests can use it directly)
client/src
  api.ts         the only place that calls fetch
  hooks.ts       TanStack Query hooks
  format.ts      time formatting, initials, and the overdue rule
  components/    SummaryStrip, Roster, VisitViews, RecordVisitSheet, PersonCombobox
  components/ui/ shadcn/ui components (generated by the shadcn CLI, owned by the repo)
docs/decisions.md
```

## API

| Method | Path | Notes |
| --- | --- | --- |
| GET, POST | `/api/clinicians` | List includes `visitCount` and `lastVisitAt` |
| GET | `/api/clinicians/:id` | 404 if not found |
| GET, POST | `/api/patients` | List includes `visitCount` and `lastVisitAt` |
| GET | `/api/patients/:id` | 404 if not found |
| GET | `/api/visits?clinicianId=&patientId=` | Newest first; both filters optional and combinable |
| POST | `/api/visits` | `{ clinicianId, patientId, visitedAt (ISO 8601), notes? }`. 400 invalid input, 422 unknown clinician or patient |

Errors always look like `{ "error": "...", "details": [{ "path", "message" }] }`.

## What I'd do next

- **Before real patient data (HIPAA):** authentication, role-based access (a clinician sees only their assigned patients), an audit log of every read and write, encryption at rest, and no PHI in logs or URLs.
- Postgres with migrations, and UUIDs instead of sequential ids.
- Cursor pagination on `(visited_at, id)` and server-side search.
- Editing and soft-deleting visits; an overdue threshold set per patient's care plan instead of one global constant.
- CI running tests, typecheck and lint on every pull request; an end-to-end test with Playwright.
